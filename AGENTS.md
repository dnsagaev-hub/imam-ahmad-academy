# Академия имама Ахмада — правила проекта

Сайт онлайн-школы ханбалитского фикха «Академия имама Ахмада»: курсы по 4 ступеням, уроки с тестами,
статьи и разборы вопросов, библиотека книг, время намазов. Владелец сам наполняет сайт через админку,
код пишет ИИ.

Что и зачем — `docs/PRD.md`. Как устроено — `docs/ARCHITECTURE.md`. Реестр задач — `TASKS.md`,
открытые вопросы владельцу — `QUESTIONS.md`. **Как ведётся задача — `docs/tasks/README.md`.**
`README.md` в корне — инструкция для людей (запуск, наполнение, хостинг); при расхождении верны этот файл и `docs/`.

## Владелец и общение
- Владелец — русскоязычный, **новичок в программировании**. Отвечай **по-русски**, простыми словами, пошагово.
  Не используй жаргон без объяснения. Владелец работает в приложении Claude (вкладка Code) на Mac, а не в терминале:
  команды запускай сам; если что-то нужно сделать ему руками, объясняй по шагам, куда нажать.
- Часовой пояс — Москва. Компьютер — **Mac** (Docker Desktop установлен).
- Подписка Pro: проектов Claude (Projects) нет, правила для ИИ живут только в репозитории (`CLAUDE.md` → `AGENTS.md`).
- Владелец сам наполняет сайт через админку. Код пишет ИИ. Владелец код не читает: на воротах он принимает
  результат по объяснению простыми словами и по шагам проверки, которые может пройти сам (что открыть, куда
  нажать, что должно получиться), снимкам экрана и зелёной проверке CI.
- GitHub: `dnsagaev-hub/imam-ahmad-academy` (основная ветка `main`, репозиторий публичный — **никаких секретов в коде**).

## Стек
Next.js 16 (App Router, Turbopack) + Payload CMS 3.82 (админка на `/admin`) + PostgreSQL; React 19,
TypeScript 6, Node 24. Подробности — `docs/ARCHITECTURE.md`. Новая зависимость — только с согласия владельца.

## Команды
- Установка: `npm install`
- Настройки: `.env.example` → `.env`; секреты в git не попадают
- Запуск локальной версии (как у владельца, ярлык «Запустить сайт (Mac).command»): `docker compose up -d --build` → http://localhost:3000, админка `/admin`
- Разработка: `npm run dev` (нужна база, см. `docs/stendy.md`)
- Сборка: `npm run build` (база не нужна)
- Быстрые проверки перед пушем: `npx tsc --noEmit` (в CI есть) и `npm run lint` (в CI нет, на `fa9542e` не проверен)
- Миграции: `npm run migrate`, новая — `npm run migrate:create -- <имя>`
- Демо-наполнение: `npm run seed` — **только для пустой тестовой базы**
- **Полная проверка: CI «Проверка сборки» (`.github/workflows/ci.yml`) на ветке задачи** — установка, миграции,
  наполнение, типы, сборка, ответ 200 на основных страницах, снимки экрана (компьютер и телефон), Docker-образ,
  запуск через docker compose, ярлык копии данных. Зелёная — это успешный прогон **и** в `ci.log` нет
  `ОШИБКИ` и `ГОРИЗОНТАЛЬНАЯ ПРОКРУТКА`. Журнал и снимки последнего прогона — в ветке `ci-logs`
  (`status.txt` — результат, ревизия и имя ветки; `ci.log`, `shots/*.png`, `site-preview.zip`):
  `git fetch origin ci-logs && git show origin/ci-logs:status.txt`. Ветка `ci-logs` хранит только последний прогон
  любой ветки: сверяй ревизию в `status.txt` с проверяемой. Статус самого прогона — `gh pr checks` или `gh run list`.
- Стенды и проверки вне обычного прогона — `docs/stendy.md`

## Инварианты (нарушение = ошибка)
- **Данные владельца.** Он уже наполняет локальную версию; данные лежат в Docker-томах проекта
  `imam-ahmad-academy` (`db-data`, `media`), не в папке с кодом. **Никогда** не выполнять `docker compose down -v`,
  не удалять тома, не сбрасывать базу без явной просьбы. Перед любым изменением, которое затрагивает базу, предложить
  владельцу запустить ярлык «Сделать копию данных» (pg_dump и папка media в `backups/`).
- **Стартовое наполнение** (`SEED_STARTER=true`) выполняется один раз: после него в настройках стоит скрытый флаг
  `starterSeeded`, и удалённые или изменённые владельцем материалы не восстанавливаются. Не ломать этот флаг.
- **Миграции только добавляющие.** Любое изменение полей коллекций — новая миграция `npm run migrate:create -- <имя>`.
  Не переименовывать и не удалять поля: drizzle задаёт интерактивный вопрос «создать или переименовать столбец»,
  а старые данные могут пропасть (пример: поле курса `book` заменено на `books`, но `book` оставлено скрытым).
  В `up` миграции нет `DROP`. Новое значение select (enum) нельзя в той же миграции делать значением по умолчанию
  (Postgres: «unsafe use of new enum value»). Проверка: CI падает на вопросе о переименовании; `DROP` — просмотр
  файла миграции при приёмке.
- **Верные ответы тестов никогда не уходят в браузер**: поле `correct` читает только админ, проверка — серверными
  действиями `checkAnswer`/`submitQuiz`. Проверка: приёмка любого diff в уроках, тестах и запросах.
- **Персональные данные не собираются**, пока регистрация выключена (`NEXT_PUBLIC_REGISTRATION_ENABLED=false`):
  прогресс ученика — только в браузере. Включение регистрации — решение владельца (нужны политика и уведомление
  Роскомнадзора), задача уровня В.
- **Секретов в репозитории нет** (он публичный). Временные `PAYLOAD_SECRET`/`DATABASE_URL` в Dockerfile и
  `docker-compose.yml` — только для сборки и локальной версии; на хостинге задаются свои.
- **Google Fonts не использовать**: шрифты локальные (`@fontsource`); из России Google Fonts бывает недоступен
  и ломал сборку.
- **Научные материалы — ничего не выдумывать.** Содержание уроков и статей религиозное:
  - арабские цитаты — **только из источника** (оцифровки «аль-Мактаба аш-Шамиля», OpenITI, turath.io), никогда по памяти;
    каждую цитату сверять с текстом книги;
  - основное мнение мазхаба (му‘тамад) — по «Шарх Мунтаха аль-Ирадат», «Кашшаф аль-Кына‘» (аль-Бухути),
    «Матолиб Ули ан-Нуха»; если «аль-Мунтаха» и «аль-Икна‘» расходятся — приводить оба мнения;
    выборы отдельных учёных (например, Ибн Таймии) помечать как «другое мнение», а не как мазхаб;
  - хадисы — всегда указывать сборник и номер хадиса (например: «Передали Муслим (№ 2276) и ат-Тирмизи (№ 3606)»),
    номер сверять по арабскому тексту сборника; приписку «сверить на Dorar.net» не писать (решение владельца 19.10.2026);
    если номер найти не удалось — блок «Пометка» с видом «Сверить с источником»;
  - сайт объясняет книги мазхаба, **а не выносит личные фетвы** — это сказано на страницах статей и контактов;
  - сомнительное помечать блоком «Пометка» с видом «Сверить с источником».
  Задача, которая добавляет или меняет научный текст (в `src/seed` или в шаблонах страниц), в итоге перечисляет
  каждую цитату с источником, а что не сверено — в «Не проверено».

## Процесс в этом проекте
Общие правила — `docs/tasks/README.md` (из набора, в проекте не правится). Ссылка на Notion в нём владельцу
этого проекта недоступна: ядра в файле достаточно. Здесь — только то, что зависит от проекта.
- Реестр задач: `TASKS.md`. Номер задачи — число по порядку (1, 2, 3…); папка задачи — `docs/tasks/<номер из трёх
  цифр>/` (задача 7 → `docs/tasks/007/`).
- Основная ветка: `main`; ветка задачи: `task/<номер>` (например `task/007`). В `main` напрямую не пушится ничего,
  кроме автоматического коммита CI с миграцией.
- CI: «Проверка сборки» запускается на каждый пуш в `main` и на каждый PR в `main`. **Миграцию CI создаёт сам**,
  если схема изменилась, но сохраняет её в репозиторий **только на `main`** (коммит «Автоматически: … [skip ci]»).
  Поэтому в задаче, которая меняет поля коллекций, миграция создаётся в ветке задачи вручную
  (`npm run migrate:create -- <имя>`, нужна база — `docs/stendy.md`) и проходит приёмку вместе с кодом;
  CI на PR падает, если схема изменилась, а миграции в ветке нет;
  после слияния — `git pull`, если CI что-то докоммитил.
- Ворота 2 = PR на GitHub: в описании простыми словами, что изменилось для владельца, и шаги, как проверить самому
  (локальная версия или снимки из `ci-logs`); слияние PR — слово владельца. Ворота 1 (уровни Б и В) — владелец
  подтверждает в чате критерии, записанные простыми словами в `SPEC.md`.
- Тестов в проекте пока нет: поведение проверяется в CI ответами страниц и снимками. Для уровня Б и В критерий
  закрепляется проверкой в CI (страница, текст на ней, ответ сервера) или ручной проверкой с записанными шагами.
  Это исключение из ядра (там на Б и В — тест с осмысленным красным до кода) до ответа на вопрос 1 в `QUESTIONS.md`
  о тестовом фреймворке.
- Уровни на примерах этого проекта:
  - **А:** текст, подпись, стиль, отступы, перевод названия; ошибка показа при верных данных (формат даты, порядок
    в меню); правка `README.md` и документов.
  - **Б:** новая страница или блок поверх готовых данных; логика курса, тестов, прогресса и уровня ученика
    (`src/lib/learning.ts`, `localProgress.ts`); время намазов и хиджра; превращение ссылок на видео; поиск и фильтры.
  - **В:** изменение полей коллекций и миграции; всё, что касается данных владельца в Docker-томах; доступ
    (`src/access`, кто видит `correct`, админка); включение регистрации и персональные данные; хостинг, деплой,
    перенос базы и файлов на хостинг; S3 и почта.
- Научный текст (цитаты, мнения мазхаба) — отдельная строка в итоге задачи любого уровня, сверяется по правилам
  из «Инварианты».
- Необратимые действия — только с отдельного слова владельца: любые команды с Docker-томами владельца
  (`down -v`, удаление, сброс базы, `npm run seed` в его базу), запуск миграций на его базе, хостинг Timeweb
  (создание приложения, базы, бакета, переменные), перенос данных, публикация сайта и домен.

## Ловушки, на которых уже ошибались
- Google Fonts ломал сборку → только локальные шрифты.
- Переименование поля в коллекции → интерактивный вопрос drizzle и риск потери данных → только добавлять поля.
- Новое значение enum сразу по умолчанию → ошибка Postgres «unsafe use of new enum value» → две миграции.
- После слияния PR в `main` CI может докоммитить миграцию и `package-lock.json` → `git pull` перед следующей работой.
